# Explainable Churn Prediction

[![Run project](https://github.com/harsha089999/explainable-churn-prediction/actions/workflows/run.yml/badge.svg)](https://github.com/harsha089999/explainable-churn-prediction/actions/workflows/run.yml)

**A churn model that decides who to call by expected profit and explains each score in plain terms.**

> **About the data:** everything in this repo is simulated, generated by the code with a fixed random seed so results are reproducible. The numbers describe the simulation, not the real world. Each project says how to swap in a real dataset.

## The business question

Which customers are likely to cancel soon, why, and who should the retention team call first?

## What this project does

A churn model is only useful if the retention team believes it and can act on it. This project trains a baseline and a stronger model, picks the call threshold from the economics of a retention call rather than from accuracy, and produces per-customer reason codes so the output can sit in a dashboard as a call list.

## The data

6,000 simulated telecom-style customers with tenure, monthly charges, support tickets, contract type, payment method and internet service. Churn is generated from a logistic relationship: month-to-month contracts, short tenure, higher charges, more support tickets and invoice payment all raise churn risk. The columns resemble public churn datasets such as IBM Telco Customer Churn on Kaggle, so a real file can replace the generator.

## How it works

1. Split 75/25, stratified by churn.
2. Preprocess inside a scikit-learn `Pipeline`: scale numeric columns, one-hot encode categoricals.
3. Train logistic regression (baseline) and gradient boosting. Compare ROC-AUC and PR-AUC and keep the better by ROC-AUC.
4. Choose the threshold by expected profit. A call costs $15, a saved customer is worth $400 and 30% of called churners are saved. Sweep thresholds from 0.05 to 0.90 and take the most profitable.
5. Global drivers: permutation importance (the drop in ROC-AUC when a feature is shuffled).
6. Reason codes: for each customer, replace one feature at a time with a typical value (median or mode) and record how much the churn score falls. The three biggest drops become `top_reasons`.
7. Assign risk bands (Low, Watch, Call) and a `value_at_risk` (probability x $400).

## Run it

```bash
git clone https://github.com/harsha089999/explainable-churn-prediction
cd explainable-churn-prediction
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python src/main.py
```

It runs in about 15 seconds or less on a laptop and writes its files to `outputs/`. Python 3.10 or newer is recommended.

This is the actual console output when the script is run as shipped:

```text
logistic           ROC-AUC 0.797  PR-AUC 0.710
gradient_boosting  ROC-AUC 0.785  PR-AUC 0.684
Chosen model: logistic, call threshold 0.12, expected profit $48,585
         feature  importance
   tenure_months    0.139441
        contract    0.094266
 monthly_charges    0.047968
 support_tickets    0.033039
  payment_method    0.007670
internet_service   -0.000414
```

Logistic regression (ROC-AUC 0.797) edged out gradient boosting (0.785). That is expected here because the data was generated from a logistic relationship; on real data boosting often does as well or better. The chosen call threshold is low (0.12) because a call is cheap compared with the value of a saved customer. Tenure and contract type are the strongest drivers. The $48,585 expected profit depends entirely on the assumed $15, $400 and 30% (constants at the top of `main.py`); replace them with your business's numbers.

## Limitations and honest caveats

- The threshold is tuned on the same test set the profit is reported on, so the profit figure is optimistic. A separate validation split would fix this.
- Reason codes use a simple one-feature-at-a-time substitution. They are not SHAP values and ignore feature interactions.
- There is no calibration check, so probabilities should be read as scores until calibrated.
- No time dimension: real churn modelling should respect when each customer was observed.

## Using real data

Download IBM Telco Customer Churn (or your own customer table), rename columns to match `NUM` and `CAT` at the top of `main.py` and replace `make_data()` with a CSV loader.

## Turning it into a dashboard

A call list sorted by value at risk, a bar chart of top churn drivers, and filters for contract type and tenure band.

## Ideas to extend it

- Replace the reason codes with SHAP values.
- Add a survival model for time-to-churn (lifelines).
- Tune the threshold on a validation split.
- Monitor drift month to month.

Classification, cost-sensitive decision thresholds, explainability, turning an ML score into a business action.
